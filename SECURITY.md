# Security policy

This repository is a **synthetic local prototype**. Read [security architecture](docs/security/security-architecture.md), [threat model](docs/security/threat-model.md), [incident response](docs/security/incident-response.md) and [delivery evidence](docs/STATUS.md).

## Current boundary

The Fastify API requires explicit nonproduction `DEMO_MODE=1` or `LOCAL_AUTH_MODE=1`, binds loopback and rejects unexpected hosts/browser origins. Demo uses a server-selected synthetic profile; local identity uses maintained-library sessions and server-derived membership. Financial HTTP work runs with transaction-local tenant context and forced RLS. The reviewed migration chain contains 31 frozen files, including the continuation's acquisition, merchant/category, recurring, locale, XLSX, source-erasure, creation and understanding records. Identity, migration and cross-profile maintenance retain explicit trusted boundaries.

The full 16-case isolation suite ran with PostgreSQL configured and two independent same-name Unix-socket clusters: 14 cases used PostgreSQL and two local PGlite fixtures exercised unsafe-membership and quarantine guards. The cluster case was not skipped. An independent non-owner credential review also covered 24 continuation tables. Missing-context and cross-profile access are denied; immutable audits, source-receipt transitions and financial reference constraints are exercised. Both clusters applied the same 31 checksums, and verification locks/temporary runtime roles were removed afterward. Ordinary single-cluster/default suites can skip PostgreSQL-only checks; their results are separate. A runtime SQL role can set custom context values, and the local API process retains trusted authority for its named tasks. These policies address missing predicates and accidental foreign references; they do not make arbitrary SQL execution or application compromise safe. Read [PostgreSQL isolation](docs/architecture/postgresql-isolation.md) and [current evidence](docs/STATUS.md).

The local server encrypts selected financial text/raw payloads, manual audit reasons, mapping content, private merchant/category histories, recurring selectors/choices, acquisition checkpoints and saved understanding payloads through per-profile AES-GCM envelopes and an independent filesystem adapter. Explicit user corrections, raw source text and historical labels remain lossless. Rules-only/private/quiet controls suppress derived proposals and evidence without removing owned export records; hidden liabilities cannot become extra available cash. Account names, legacy merchant keys, rule definitions, other copies and complete tokenization/index coverage still require treatment. Support is bounded/audited, and telemetry uses fixed allowlists without financial content. See [profile encryption](docs/architecture/profile-envelope-encryption.md), [merchant/category decisions](docs/implementation/merchant-taxonomy.md) and [understanding persistence](docs/architecture/understanding-persistence.md).

Whole-profile deletion stages a durable intent before post-commit destruction of the current local wrapping keys. Source row erasure instead records exact owned membership in an independently fsynced HMAC journal anchored in the current vault; its shared profile DEK stays live. Old source backups can still decrypt before mandatory quarantined replay. Signed generation proofs bind actual account/transaction/observation/manual-command membership and logical content, including decrypted retained payloads and cached financial responses. A newer valid proof cannot authorize transplanted older financial content. Missing/current-journal disagreement, unknown orphan caches or foreign membership keeps recovery quarantined. Legitimate authenticated later generations may reuse IDs. Current independent records must survive database backup replacement; privileged rollback of both journal and vault and historical key copies remain outside this proof. See [source erasure](docs/architecture/source-erasure.md) and [restore](docs/operations/deletion-aware-restore.md).

Acquisition and connection creation commit reservations/intents before provider I/O and recheck profile, grant generation, consent state, deadline and lease before application. Provider discovery/grant/fetch calls do not run under the financial SQL transaction. Partial acquisition cannot advance balances or freshness. An early revocation acknowledgement cannot release an uncertain creation: a grant may settle afterward, requiring a fresh exact-generation acknowledgement. Unknown settlement remains fenced rather than inventing provider finality. These are synthetic adapter contracts; see [durable acquisition](docs/architecture/durable-synthetic-sync.md) and [connection creation](docs/reviews/local-connection-creation.md).

CSV/XLSX inputs have finite byte/row/ZIP/XML bounds and explicit mapping/preview checks; unsupported active workbook content is rejected. ICU messages translate fixed codes and validated arguments, while original source/user/legal text remains original. The browser's encrypted read-only cache holds one bounded overview under a volatile nonextractable session key, blocks actions offline, and drops its key on received invalidation/expiry and local erasure attempts. It cannot discover remote erasure while disconnected and is not a complete 90-day server projection, cold offline login or native keystore. See [offline limits](docs/operations/offline-cache.md) and [localization](docs/architecture/localisation.md). Keep all fixtures synthetic; do not expose local modes publicly or load real financial records.

Implemented scenario tests do not establish production RLS, passkeys/MFA, TLS/KMS field encryption, WAF, secret-manager operation, backup/PITR recovery, GDPR rights completion, penetration testing or legal clearance. These are explicit real-data prerequisites in the security/compliance documents. The API's production rejection is intentional.

## Reporting a vulnerability

A monitored security email and response SLA have **not been established**. The former placeholder email is not a reporting destination. If GitHub private vulnerability reporting is enabled for the repository, use it; otherwise use an existing private maintainer contact to arrange confidential disclosure. Do not publish secrets, personal financial records or exploitable confidential details in a public issue. Do not access another person's data or run destructive, denial-of-service or social-engineering tests.

## Contributor requirements

- Never commit credentials, production tokens/certificates, bank credentials, full PAN or real personal financial fixtures. Environment examples contain local demo values only; actual secrets require the approved future secret-management process.
- Keep demo bind/origin/host and production guards intact. A profile ID/header from a client is not authenticated authorization.
- Preserve exact-money/valid-date checks, bounded input/cursors and profile references. Test stale revisions, duplicate/reordered inputs, replay, partial failure and unauthorized identifiers where relevant.
- Keep provider I/O outside financial SQL locks. Do not equate a delayed request, user-present checkpoint, revoked grant or early revocation acknowledgement with current authority. Recheck generation/lease/source guards before committing financial facts.
- Preserve canonical signed receipt/intent/journal bytes and UTC clocks. Compatibility with offset-bearing external version-1 export metadata must compare actual instants without rewriting signed records or weakening MAC/scope checks.
- Logs/traces/analytics must exclude tokens/cookies, raw provider payloads, transaction descriptions, account identifiers, amounts and sensitive categories. Debug/error handling must not bypass these rules.
- External AI/OCR is not enabled by the mock. Any future integration needs a permitted purpose/basis, approved processor/endpoint/retention/transfer terms, minimal tenant-scoped data, actual permission where required and evaluation. Pseudonymisation is not anonymity.
- Follow the current retention/purpose schedule. Cold storage is not deletion; a live key deletion does not prove backup erasure. Real-data export/delete requires subject authorization, complete derivative/processor handling and tested restore-tombstone replay.
- Do not remove production recovery records to make tests pass. Disposable teardown may remove only its own exact synthetic UUID fixtures under a trusted boundary, restoring audit guards transactionally before destroying its temporary signer. Unknown production receipts/caches must retain the restore guard.
- Review lockfile/dependencies and secrets. CI config includes secret scanning and an advisory dependency audit; configured jobs are not executed findings, and an audit with `continue-on-error` is not a release security gate.

## Real-data release prerequisites

Before any real-bank pilot, implement and verify production identity/session/recovery and profile membership isolation, appropriate storage/transport/key/secret protections, privacy/retention/rights and backup/restore controls, response/logging safeguards and incident ownership. Resolve or independently validate mitigations for open dependency advisories in the actual release path and rerun the audit. Obtain the written acceptable licence route, provider permission/contract, processor/privacy/DPIA/taxonomy assessment and informed participant consent. Store billing/native-device release and household sharing require additional lifecycle/isolation checks. No document alone clears these gates.

The full E00–E39 programme remains partial. Generic no-ID/ID-churn reconciliation, complete pending/own-IBAN decisions, FX provenance, scoped server search/90-day projection, full feedback/rule actions, fitted calibration/runtime policy, exact connection gaps and wider protection/retention are genuine remaining local P0 work. They can progress without real-bank credentials or legal acceptance. The [execution plan](docs/product/execution-plan.md) distinguishes that engineering from specific external evidence; evaluation tools train/promote no model and synthetic/browser tests establish no actual user acceptance.

This project is pre-release, with no supported production versions or published security SLA. Fixes follow the actively reviewed development branch; do not assume a production support guarantee from `main` or the current branch name.
