# Local content-free notifications — E17.1

The local in-app feed, scoped preferences, consent-term reminders and read state are implemented. Native push, APNs/FCM registration, device permission prompts and external delivery are unavailable. The API reports `nativePushAvailable: false` and `osPermission: unknown`; a local preference is never evidence of operating-system permission or provider delivery.

## Permission and payload boundary

Optional inbox, renewal, verification, connection-state and summary notices require the current `N-SERVICE` disclosure to have an explicit granted local preference. The initial permission is off. Each optional kind has its own preference. Security, export, deletion and mandatory data-rights notices bypass optional permission, optional preferences, quiet hours and the optional-notification configuration switch. The current actual producers are successful user-initiated `POST /v1/export/archive` and sync results containing review items; status/reminder discovery also reads saved consent lifecycle facts. Export GET routes remain read-only. Registering a notice type does not establish another producer or live delivery capability.

Feed payloads contain an opaque event UUID, a bounded event kind, one fixed Italian generic title, text version and delivery/read metadata. There are no amounts, transaction descriptions, merchants, bank names, account names, financial identifiers or user identifiers in titles or encoded delivery payloads. Connection references remain in scoped local SQL and are available only through an owned event destination request. No public route can publish a notification. Exported ownership records include private references and the immutable notification journal under the normal rights boundary; exports are not anonymous telemetry.

## Scheduling and concurrency

`NotificationsService` resolves the caller's financial profile; the HTTP boundary supplies the validated principal. Preference writes and mark-read commands require the current revision. Profile locks serialize scheduling, suppression, publishing and read mutations. The immutable SQL journal refuses modification independently of TypeScript, and all notification data cascades during profile erasure. Withdrawn optional permission invalidates queued entries, including withdrawal followed by a grant before the next pump. Delivered history remains delivered.

The bounded trusted pump validates runtime configuration before selecting profiles, advances a fair private profile cursor and limits rows per profile. Consent discovery has a safety cap of 100 connections; pending entries referencing additional connections are validated separately before delivery. No unbounded complete-discovery or production throughput claim follows from that cap.

Reminder scheduling uses only provider-declared required actions with known future dates. Consent renewal, SCA and provider-session renewal remain distinct actions. Unknown dates and undocumented renewal methods do not create guessed deadlines. UTC offsets in declared dates are normalized. The deduplication key binds the consent generation, action, declared deadline, configured relative offset and text version. Renewal—even with the same consent ID—cancels queued old-generation reminders. Revocation, pause, changed deadlines and fulfilled actions cancel pending entries; already delivered entries retain their history.

Runtime configuration supplies versioned offsets. `DEFAULT_NOTIFICATION_CONFIGURATION.expiryOffsetsSeconds` is empty: reminder windows need an explicit configuration revision. Missed past offsets are not fabricated or caught up. Quiet hours use the actual profile IANA time zone through `Intl`, including overnight intervals and DST transitions. Inbox delivery is capped at one per local calendar day, including notices queued during the previous day's quiet period.
