## 0. Executive summary (decision-relevant)

1. **No PSD2 identifier is universally stable.** The Berlin Group `transactionId` is defined only as an access key for the transaction-details call; `entryReference` is the field meant for delta/reference use (same id as in camt.05x) — and FinecoBank, an Italian bank, declares both `entryReference` and `endToEndId` "currently not used", and does not support `bookingStatus=pending` at all (FACT, Fineco's own OpenAPI). Enable Banking's FAQ says exactly this: use `entry_reference` for matching across retrievals, never `transaction_id`, and expect `entry_reference` only on BOOK transactions (FACT). Salt Edge says pending ids can change and recommends deleting all pending rows on every fetch (FACT). TrueLayer says `transaction_id` may change between requests and recommends `normalised_provider_transaction_id` (FACT). Plaid replaces a pending record with a new posted record carrying `pending_transaction_id` (FACT). Yapily fabricates a `transactionHash` when the institution has no native id — and its own docs say the hash "is not guaranteed to be completely unique or immutable" and "may change or result in duplicates if the underlying data is updated by the institution" (FACT [AV2], S48). **Design consequence:** ingestion identity must be layered: provider-stable id → vendor id → content fingerprint with an occurrence ordinal → fuzzy window. Never make the bank id the primary key.
2. **Every serious OSS PFM uses the same two-stage dedup:** exact import id first, then an amount-equal, date-window fuzzy match (YNAB ±10 days, Actual ±7 days, beangulp ±2 days with 5% amount tolerance, Maybe ±4 days for transfer pairing, Actual's transfer script ±3 days). YNAB's `import_id` format `YNAB:[milliunit_amount]:[iso_date]:[occurrence]` is the canonical "fingerprint + ordinal" scheme (all FACT, source code/specs).
3. **Ledger shape:** a "double-entry-lite" model — one posting per real account per observed movement, with explicit *links* (transfer pair, card settlement, refund, split, reimbursement) rather than a full double-entry journal — matches how Maybe (Transfer with inflow/outflow + `RejectedTransfer`), Actual (`transferred_id` + transfer payee) and YNAB (`transfer_transaction_id`) actually work, while keeping an append-only event log for undo and provenance. Store money as `bigint` minor units + ISO code + scale; Dinero.js **v2 is now stable (2.0.0 on 2026-03-02, 2.0.2 on 2026-03-13, MIT, `dinero.js/bigint` entry point)** (FACT, npm registry; re-verified [AV]: the package `exports` map exposes `.`, `./currencies`, `./bigint` and `./bigint/currencies`, and `engines.node` is `>=20.0.0`).
4. **Dates:** PSD2 gives `bookingDate`/`valueDate` as calendar dates (no time), and some providers render them as midnight-UTC timestamps; treat the analytics date as a `DATE` in Europe/Rome and never convert through UTC timestamps. Value date ≠ booking date for analytics; card transactions additionally have a `transaction_date` (Enable Banking exposes all three — FACT).
5. **Postgres RLS is the right isolation primitive for households** but table owners bypass it unless `FORCE ROW LEVEL SECURITY`, and superusers/`BYPASSRLS` roles always bypass (FACT, PG 18 docs). pgcrypto's own docs say that if you cannot trust the DBA you should "do crypto inside the client application" and that its raw `encrypt()` functions lack integrity checks (FACT) → use app-level AES-256-GCM envelope encryption with KMS-wrapped data keys for IBANs and raw descriptions.
6. **Licences:** Firefly III, Maybe (and its live community fork Sure), Ghostfolio are **AGPL-3.0**; Actual Budget is **MIT**; Frankfurter is **MIT**; beangulp is **GPL-2.0-only** (all FACT from licence files/package manifests, re-read in the adversarial pass). The upstream `maybe-finance/maybe` repository is **archived** (GitHub API `archived: true`, last push 2025-07-24) and `we-promise/sure` is the live successor (last push 2026-10-02) (FACT [AV], S41). Study AGPL code freely; only MIT/Apache code may be copied into a proprietary SaaS without AGPL obligations.

**Booked vs pending lists.** The transactions resource returns `transactions.booked[]` and `transactions.pending[]` (and, in BG ≥1.3.8, `information[]`); the query parameter `bookingStatus` accepts `booked`, `pending`, `both` (and `information`). Fineco: "The only permitted code is 'booked'. 'pending' and 'both' are not supported (error code is returned because not supported)" and "'pending' transactions list is not supported" (FACT, S11). GoCardless' sample shows a pending entry with **no `transactionId` and no `bookingDate`**, only `valueDate` + amount + remittance text (FACT, S6). Enable Banking's status enum is richer: `BOOK`, `PDNG`, `CNCL` (cancelled), `HOLD`, `RJCT` (rejected), `SCHD` (scheduled) (FACT, S3).

**Balances** (for completeness): `balanceType` values include `closingBooked`, `expected`, `interimAvailable`, `interimBooked`, `forwardAvailable`, `authorised` (sibling doc §2.4, medium-high).

### 2.2 Synthesis: fingerprint design rules supported by the evidence

1. **Hash only slowly-varying fields.** Firefly's whole-row hash breaks on capitalisation and id churn (FACT). Fingerprint inputs should be: account (internal id), signed amount in minor units, currency, a *date bucket* (booking date for booked; value date or transaction date for pending), and a **normalised** description (uppercase → lowercase, collapse whitespace, strip card-masking digits, dates, auth codes, "PENDING/RESERVED" prefixes). Everything else (counterparty IBAN, bank codes) belongs in the *evidence*, not the hash.
2. **Add an occurrence ordinal** (YNAB `:occurrence`, Yapily `.1`): within one (account, date, amount, normalised description) group, number the rows in provider order. This keeps two identical €1.20 coffees distinct while still being deterministic across re-fetches — as long as provider order is stable (ASSUMPTION; mitigate with `balanceAfterTransaction` ordering when present). [AV2] Yapily's hash uses essentially this input set (account, institution, credit/debit, date, amount, description + same-day rank) and Yapily explicitly warns it "may change or result in duplicates if the underlying data is updated" (S48) — independent confirmation that a fingerprint is a *matching* key, not an identity, and that description edits by the bank are the main churn source (hence normalise aggressively).
3. **Windows:** ±7 days for CSV-vs-API dedup (Actual), up to 10 (YNAB), 2–4 days for transfer pairing (beangulp 2, Actual script 3, Maybe 4). For pending→booked, booking usually lands 1–5 days after the authorisation but the tail is long (TrueLayer: up to 120 days) — use a provider-configurable window with default 10 days and a secondary "late" pass up to 45 days with stricter description similarity.
4. **Amount equality for dedup; amount tolerance only for state transitions** (pending→booked tips/FX, beangulp 5%, Maybe 5% cross-currency). Never fuzzy-match amounts across *different* sources without a description/counterparty signal.
5. **Scope ids by account and source** (Actual `${account}-…`, YNAB "unique by account", Tink "unique per user and account"). Provider ids are not globally unique.
6. **Respect locks and user edits** (Actual `reconciled`, Sure "locked" attributes — sibling AI doc, ASSUMPTION) — an automated re-match must never overwrite a user decision; it may *propose*.
7. **Remember rejections** (Maybe `RejectedTransfer`) so undo is sticky.
8. **CSV vs API duplicates:** CSV rows have no provider id; their fingerprint must be computed with the *same* normaliser as API rows, and the CSV importer must declare its date semantics (Italian exports usually carry both "Data" (booking) and "Valuta" (value) columns — ASSUMPTION; sibling S33 documents Intesa/UniCredit/Fineco CSV formats). Match CSV→API by fingerprint first, then ±7-day amount window with description similarity ≥ threshold; mark the CSV row as `superseded_by` the API row rather than deleting it.

### 3.2 Immutability / event sourcing vs mutable rows

- Evidence that *inputs* are mutable: Plaid "posted transactions are not strictly immutable" (FACT); Yapily `transactionMutability` (FACT); Tink deletes/re-inserts (FACT); Salt Edge pending rows change ids (FACT). Evidence that *user state* must be protected: Actual ignores `reconciled` matches and keeps existing payee/category/notes on update (FACT); Firefly's hash is frozen at import so later edits do not affect dedup (FACT).
- Pattern that reconciles both: **immutable `provider_record` (raw payload + extracted fields, versioned per fetch) → mutable canonical `transaction` row (current state) → append-only `ledger_event` (who/what/why changed it)**. Full event sourcing (rebuilding state from events only) is not required for a PFM and complicates queries; CQRS-style "events + materialised current rows" gives undo, provenance and explainability at modest cost (ASSUMPTION, standard practice).
- Keep provider payload versions for 90 days (then pseudonymise/aggregate — see §7); keep events indefinitely (they are the audit trail).

### 4.2 Recommended modeling for Lilleri

- **Core tables (sketch).**
  - `account(id, household_id, kind ∈ {current, card_credit, card_prepaid, cash, savings, loan, external}, currency, …)` — card_credit is a **liability** (balance = amount owed).
  - `provider_record(id, connection_id, source ∈ {psd2:<aggregator>, csv, manual, email}, provider_key, fetched_at, status_raw, payload jsonb, fingerprint, ordinal, superseded_by)` — immutable.
  - `transaction(id, household_id, account_id, amount_minor, currency, scale, booking_date, value_date, transaction_date, status ∈ {pending, booked, cancelled, reversed}, description_raw_enc, description_norm, counterparty_name, counterparty_iban_enc, counterparty_iban_hash, bank_code_iso, bank_code_prop, mcc, category_id, merchant_id, kind ∈ {standard, transfer, card_settlement, cash_withdrawal, refund, reimbursement, fee, interest}, parent_id, locked_fields jsonb, version)`.
  - `transaction_source(transaction_id, provider_record_id, role ∈ {primary, pending_predecessor, duplicate_csv, duplicate_provider})` — n:1 history of records that fed the row.
  - `link(id, household_id, type ∈ {transfer_pair, card_settlement, refund_of, reimbursement_of, split_of, reversal_of, shared_expense}, from_transaction_id, to_transaction_id, amount_minor, status ∈ {proposed, confirmed, rejected}, evidence jsonb, algorithm_version, decided_by, decided_at)` — `rejected` rows are the Maybe-style negative memory.
  - `ledger_event(id, household_id, occurred_at, actor ∈ {user:<id>, rule:<id>@<v>, model:<name>@<v>, provider:<name>, system}, entity, entity_id, op, before jsonb, after jsonb, evidence jsonb, reversible bool, reversed_by_event_id)`.
- **Transfers:** pair postings with opposite amounts (exact for same currency; FX-tolerant 2–5% for cross-currency with the dated rate as evidence), different accounts, same household, |Δdate| ≤ 4 days (Maybe) — extend to 7 for SEPA ordinary credit transfers that cross weekends (ASSUMPTION; [AV2] the Sure fork reached the same conclusion from the other side: automatic matching stays at 4 days but user-confirmed pairs are allowed up to 30 days, and the FX band is an operator setting — so make both the auto window and the tolerance per-household/per-provider parameters rather than constants). Strong evidence boosts: `creditorAccount.iban`/`debtorAccount.iban` equals the other account's IBAN (hash-compare), `endToEndId` equal on both legs, Salt Edge `mode = transfer`, Tink `parts[].counterpartTransactionId`, description contains the other account's name/IBAN fragment. Spend reports exclude confirmed transfer legs; budgets never see them (Copilot semantics).
- **Credit-card settlement (Italy):** the card account's monthly statement total is paid by one debit on the current account ("addebito estratto conto" / "pagamento carta di credito"); model it as a `card_settlement` link from the current-account debit to the **card account's statement period** (not to a single card transaction), i.e. `link.to_transaction_id` NULL and `evidence.statement_period = {from, to, expected_total}`; the card's own transactions carry the spend. Matching rule: debit on current account with amount = sum of card postings booked in the statement period and date within the settlement window. The Italian convention of settling around the **15th of the following month** (Nexi/CartaSi "a saldo", bank-issued cards; Amex around the same) is an **ASSUMPTION (medium)** — verify on real statements for Nexi, Intesa, UniCredit, Fineco, Amex IT and make `settlement_day` a per-card parameter learned from history. Amex Italy and Nexi credit cards are mostly **not** reachable via PSD2 AIS (sibling doc A §2.3) → card postings will often come from CSV/XLSX exports (sibling S33: Amex IT Excel/CSV, Nexi Excel/PDF), so the settlement link must also work when the card side is imported later or never ("unexplained settlement" state).
- **Cash wallet:** ATM withdrawal (ISO BTC domain `PMNT`, family `CCRD`, subfamily `CWDL` = cash withdrawal — ASSUMPTION for the official code list because iso20022.org is blocked, but corroborated [AV] by two independent PSD2 integrations found via GitHub code search (S46): one tests `bankTransactionCode === 'PMNT-CCRD-CWDL'` on Nordigen/GoCardless rows, another maps `PMNT/CWDL` → "CashWithdrawal" for Enable Banking's `bank_transaction_code` (medium); proprietary "PRELIEVO ATM/BANCOMAT" text — ASSUMPTION) → auto-create a `transfer_pair` to the household's `cash` account; cash spending is manual. Deposits of cash are the reverse.
- **Refunds:** a credit on the same account whose description/merchant matches a prior debit (merchant equality, amount equal or smaller, within 90 days) → `refund_of` link; category inherits the original; spend reports net them in the original period or the refund period (setting). Partial refunds allowed (amount ≤ original; cumulative refunds ≤ original enforced).
- **Reimbursements (someone pays you back):** credit from a person (SEPA transfer, Satispay, PayPal) linked `reimbursement_of` to one or more debits; reduces the "net spend" of the linked transactions; if the household uses shared-expense tracking, the reimbursement settles an `owed` balance (Splitwise semantics: `paid_share` vs `owed_share`).
- **Shared expenses:** per transaction, optional `shares[]` (`profile_id`, `owed_share_minor`), summing to the amount; `paid_share` is implied by the account owner; running `balance(profile_a, profile_b)`; a reimbursement link settles balances. This is Splitwise's model reduced to one household (FACT on Splitwise fields; design is HYPOTHESIS).
- **Reversals / chargebacks:** never delete a booked posting on provider deletion; set `status = reversed` with a `reversal_of` link to the compensating posting when one appears (Plaid: refunds modify posted rows; Enable Banking statuses `CNCL`/`RJCT`; Tink deleted-ids webhook). A provider deletion of a *booked* row with user edits becomes a "needs review: bank removed this" item, not a silent delete.

### 4.3 Pending → booked state machine (per canonical transaction)

```
                 provider pending row (no stable id)            provider booked row
                 ───────────────────────────────────            ───────────────────
 [absent] ──seen pending──▶ (PENDING) ──matched to booked row──▶ (BOOKED)
                                │  ▲                                 │
                                │  │ re-seen pending (same fp)       │ provider modifies (amount/desc)
                                │  └──── update, keep edits          ▼
                                │                               (BOOKED, version+1)  ── provider deletes ──▶ (REVERSED | NEEDS_REVIEW)
                                │
                                ├── not re-seen for > expiry (default 10 d, max 120 d)
                                │     and no booked match ─────────▶ (EXPIRED_HOLD)  [hidden; still in audit]
                                │
                                └── provider says CNCL/RJCT ───────▶ (CANCELLED)

 Match PENDING→BOOKED by: (1) provider link (Plaid pending_transaction_id, Tink PENDING_IDS,
 Enable Banking entry_reference present on PDNG); (2) same account, same amount, booked_date ≥ pending_date,
 Δ ≤ window, normalised-description similarity ≥ 0.6; (3) same account, amount within tolerance
 (configurable, e.g. ≤ 15% or ≤ €2 for tips/FX; fuel pre-auth special case), description similarity ≥ 0.8.
 User edits (category, notes, splits, links) carried over on every transition; evidence stored on the link.
```

 fetched ──exact provider id known──▶ (IDENTIFIED) ──existing row with same (source, account, key)──▶ (DEDUP_HIT: update if changed, else no-op)
   │                                         └──none──▶ (NEW) ──▶ create transaction + transaction_source
   └──no provider id──▶ compute fingerprint+ordinal ──▶ (FINGERPRINTED)

## 9. Recommendations (concrete)

### 9.1 Identity strategy for idempotent ingestion

**Primary key of `provider_record`:** `(connection_id, source_kind, provider_key)` where

```
provider_key =
  1. ASPSP stable id when the provider marks it stable:
       Enable Banking entry_reference (BOOK rows; PDNG only if present),
       Berlin Group entryReference (direct/CBI Globe; only after the per-bank fill-rate study says it is stable),
       TrueLayer normalised_provider_transaction_id,
       Plaid transaction_id, Tink id, Salt Edge id (vendor ids — stable within that vendor),
       GoCardless transactionId (booked) else `${account}-${internalTransactionId}` (booked only);
  2. else fingerprint_v1 = sha256(account_id | date_bucket | amount_minor | currency | description_norm) + ":" + ordinal
       date_bucket = booking_date for booked rows; value_date ?? transaction_date for pending rows;
       ordinal     = 1-based index among rows with the same hash in the same fetch (YNAB occurrence rule);
  3. CSV rows always use rule 2 with source_kind = csv:<mapping_id>.
```

Rules: (a) store the raw provider ids **and** the fingerprint on every record so you can switch keys later without re-fetching; (b) version the normaliser (`fingerprint_v1`, `v2`…) and keep both during migrations; (c) a record with a provider id never fuzzy-merges with another record that also has a (different) provider id from the **same** source (Actual's `strictIdChecking`), but may merge across sources (CSV ↔ API); (d) pending records are replaced wholesale per account per fetch (Salt Edge advice) — identity of a pending *transaction* lives on the canonical row, not the record; (e) sync always re-fetches a trailing window (≥ 7 days; 30 recommended) and treats absence of a previously seen **booked** record within the window as "provider deleted" only after two consecutive fetches (guards against partial responses); (f) idempotency of the sync job itself: `sync_run(id, connection_id, window_from, window_to, provider_cursor, status)` and `provider_record.sync_run_id`, so a retried run re-applies deterministically.

### 9.2 Reconciliation match types and the evidence model

| Match type | Candidate generation (blocking) | Scoring features | Auto-apply threshold (initial) | Reversible |
|---|---|---|---|---|
| `EXACT_ID` | same source + provider_key | — | always | no (it is identity) |
| `PROVIDER_LINK` | `pending_transaction_id` / `PENDING_IDS` ([AV2] **not** Yapily `transactionHash` equality — Yapily documents the hash as possibly changing or duplicating, so hash equality is a `FINGERPRINT`-class match, not a provider link) | — | always | yes (if provider later contradicts) |

| `FUZZY_WINDOW` | same account, same amount, |Δdate| ≤ 7 (CSV/API) | desc_similarity (Jaro-Winkler/ token-set), date_delta, competing-candidate count | ≥ 0.85 and unique candidate; else propose | yes |

| `TRANSFER_PAIR` | different accounts, same household, opposite amounts (exact; FX ±5% with dated rate), |Δdate| ≤ 4 (7 for SEPA ordinary) | iban_hash_match, e2e_id_match, provider_hint (Salt Edge `mode=transfer`, Tink `parts`), desc contains other account's label, bank_code (ICDT/RCDT), date_delta | ≥ 0.9 or (iban_hash_match ∧ amount exact) | yes; rejection stored |

| `SPLIT` | user or rule (e.g. Amazon multi-item) | — | user | yes |
| `REVERSAL_OF` | provider status CNCL/RJCT, deletion of booked row, or equal-opposite within 3 days with "STORNO/ANNULLO" descriptor (ASSUMPTION on Italian wording) | descriptor, provider status | auto when provider-stated; propose otherwise | yes |

Evidence record (stored on `link.evidence` / `ledger_event.evidence`): `{match_type, algorithm_version, score, features:{…}, candidates_considered, decided_by, decided_at, provider_hints:[…]}`. Every auto decision below 1.0 is shown in a review inbox with a one-line human explanation generated from the features (no LLM needed).
