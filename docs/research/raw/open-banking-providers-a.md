## Scope note and method

- **Scope.** Capability matrix, licensing routes, pricing signals, Italian coverage and reliability signals for four aggregators (group A). Group B providers (GoCardless Bank Account Data, Enable Banking, Fabrick, Plaid, Finleap/Qwist, etc.) are only cited here as licensing comparators.
- **Method.** 30 distinct WebSearch queries (English and Italian, incl. site-specific queries) were executed successfully; the session's shared search budget was exhausted on the 31st–40th queries, so some second-pass verifications could not be run (they are listed as UNKNOWN with a verification path). WebFetch was egress-blocked for every domain tried (enablebanking.com, tinkitaly.statuspage.io, docs.yapily.com, saltedge.com). To compensate, the **official developer documentation of all four providers was queried through the Context7 documentation index** (20 queries), which mirrors docs.tink.com, docs.truelayer.com, docs.yapily.com and docs.saltedge.com. Those citations are graded "high (official docs via index)" — the index may lag the live docs by weeks, so re-check before contracting.
- **Reliability scale.** high = official/primary (regulator, EUR-Lex, provider docs/legal pages); medium = reputable secondary (trade press, law-firm briefings, provider marketing); low = blogs, forums, aggregator review sites, pricing-listing sites.
- **Date caveat.** Several third-party coverage numbers (e.g. "12 Italian banks", "100+ Italian APIs", "80% coverage") date from 2019–2021 launch press; they are historical and must be refreshed by pulling each provider's live provider list in sandbox (all four expose a providers/institutions endpoint filterable by country `IT`).

### 2.4 Berlin Group NextGenPSD2 fields and how each provider surfaces them

The NextGenPSD2 XS2A framework is "the de facto reference in DACH, Northern Europe and much of Italy" (Agenda Digitale/Berlin Group; https://www.berlin-group.org/psd2-access-to-bank-accounts , high). Standard transaction fields (per XS2A implementation guidelines, e.g. Cedacri's Italian implementation https://developer.cedacri.it/images/components/com_apiportal/assets/tnc/Cedacri-NextGenPSD2-XS2A-Framework-Implementation-v1-2.pdf and HUB's definition https://www.hub.hr/sites/default/files/inline-files/API%20Definition_HUB_1_2%20web_en.pdf — medium): `transactionId`, `entryReference`, `endToEndId`, `mandateId`, `bookingDate`, `valueDate`, `transactionAmount`, `creditorName`/`creditorAccount`, `debtorName`/`debtorAccount`, `remittanceInformationUnstructured` (140 chars), `remittanceInformationStructured`, `purposeCode`, `bankTransactionCode` (ISO 20022 domain/family/subfamily), `proprietaryBankTransactionCode`, `additionalInformation`; transactions are split into `booked` and `pending` arrays (`bookingStatus=both`); balances carry `balanceType` (e.g. `closingBooked`, `expected`, `interimAvailable`, `forwardAvailable`, `authorised`).

## 7. Product-design implications for Lilleri (from the mechanics above)

1. **Expect 90 days of history on first connection**; design the onboarding promise accordingly ("understands the last 3 months immediately; learns forward") and offer optional CSV/statement import for deeper history. Verify per bank (Salt Edge `max_fetch_interval`, Yapily `transactionFrom`).
2. **Refresh budget:** 4 background refreshes/day per consent. Schedule e.g. 06:30 / 12:30 / 18:30 / 22:30 local, and use user-present refresh (unlimited) when the app is opened. With Salt Edge/Tink the scheduler is managed; with Yapily/TrueLayer build it and respect `ACCESS_EXCEEDED`. **[AV]** Page transaction requests in **≤14-day windows** (Intesa Sanpaolo enforces a two-week retrieval window per Yapily's docs) and make the window size a per-bank parameter; a catch-up after a long gap at Intesa may need several background slots or a user-present session.
3. **Consent renewal every 180 days (EEA) with bank SCA**; renewal >90 days late creates a history gap → in-app reminders from day 150, and a "reconnect" inbox item.
4. **Reconciliation keys:** store the provider's stable id (Tink `providerTransactionId`, TrueLayer `normalised_provider_transaction_id`, Yapily `id`, Salt Edge `id` + `duplicated`), `bookingDate`+`valueDate`, amount, and the raw description; pending→booked transitions change ids at many banks, so match on (account, amount, date±3d, normalised description).
5. **Credit cards:** do not promise Nexi credit-card or Amex coverage in Italy for the MVP; prepaid (Postepay, Hype) and bank-exposed card accounts are the realistic scope.
6. **Trust/UX:** under licence-as-a-service the provider's name appears on the bank consent screen; prepare copy explaining "Lilleri uses [Provider], an authorised AISP" and build the mandatory consent-management screen.
7. **Avoid lock-in:** persist raw provider payloads and map to an internal canonical schema modelled on Berlin Group fields (§2.4), so that a provider switch (e.g. Salt Edge → Tink) is a connector change.
