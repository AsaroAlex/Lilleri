# Profile envelope encryption and the independent local key vault

The synthetic API has an application encryption boundary using Node's standard AES-256-GCM implementation. A profile receives a random 32-byte data-encryption key (DEK). The database stores that DEK only after wrapping it through `KeyManagementPort`. Sensitive text uses a fresh random 12-byte nonce and a 16-byte authentication tag. Financial amounts remain exact integer values: encryption does not introduce floating point, currency conversion or a total across currencies.

`ProfileEncryption` supplies explicit text/JSON methods and transaction adapters for description, merchant name and reference. The local server also encrypts raw source-observation JSON payloads, manual balance-audit reasons, saved CSV mapping names/definitions and CSV mapping-history snapshots. It passes decrypted rows to financial/rule engines and authorized exports. A controlled startup upgrade handles existing stores before serving requests. These targeted fields do not prove every content copy is encrypted: account names, merchant keys, user rule definitions, audit snapshots outside the stated targets and export buffers still need separate treatment. Better Auth's factor encryption remains owned by that library.

## Format and authenticated context

The field format is `lilleri:v1:` followed by a canonical base64url JSON envelope containing only `keyId`, `nonce`, `ciphertext` and `tag`. Wrapped DEKs have their own `lilleri-dek:v1:` domain. Both parsers reject unknown versions, unexpected fields, noncanonical encoding, wrong lengths and oversized content. Field plaintext is bounded to 1 MiB and verified as UTF-8 during decryption. Legacy plaintext is rejected by the decryptor; an explicit, bounded, transactional upgrade must encrypt it before a server starts serving the upgraded store.

Additional authenticated data binds the format version, field/DEK purpose, profile ID, table, column, row ID and key ID. Copying ciphertext to another row, field or profile fails authentication. Each field uses its database column name, including `merchant_name`; renaming a column or changing row IDs therefore requires an explicit re-encryption migration. Keys are not cached globally. Unwrapped DEK and derived-key buffers are cleared when each operation ends. This reduces lifetime of those buffers; JavaScript does not promise physical erasure of every memory copy or plaintext string.

Equality lookup uses an HMAC-SHA-256 blind index with a separate key derived through HKDF-SHA-256. The derivation binds profile, table and column, so an equal normalized IBAN in a different domain has a different index. The caller explicitly normalizes the value. These indexes reveal equality within their domain, remain personal data and are unsuitable as public identifiers. The presence of this tested primitive does not establish that an account-IBAN integration exists.

## Synthetic adapter boundary

`createLocalSyntheticKeyManagement({directory, mode})` requires explicit `demo` or `local-auth` mode. The independently stored directory uses permissions 0700; wrapping-key files use 0600 and are checked for ownership and permissions on read. Key-file opens reject symlinks. There is a different random wrapping key for every DEK, rather than one everlasting master key that could decrypt an erased profile's old database backup.

The directory belongs outside the database backup. A database backup contains a wrapped DEK and ciphertext, but not its wrapping key. Reopening the current vault preserves live keys. A profile destruction marker is persisted and directory-synced before key files are removed. The marker prevents new profile key creation and refuses unwrapping old restored key rows. Startup cleans key files left behind a marker by interrupted destruction. An unexpected file or malformed marker fails closed. At most 1,000 candidate keys per profile are allowed; candidates prepared by a rolled-back transaction may remain inaccessible to the database until profile destruction removes all its key generations. Transaction locking and the database's unique profile key prevent competing committed keys.

This is a synthetic filesystem key provider, not a cloud KMS, HSM, secret manager, production key backup or attestation. Local root access, a copied older vault, disk remanence, memory captures and unexpired vault snapshots are outside the proof. A production adapter must supply independent authorization, durable key lifecycle, key-copy inventory, provider-specific destruction evidence, rotation/re-wrap and approved recovery arrangements. No “unreadable in every backup” claim follows from this adapter.

## Erasure and crash recovery

Migration `0014_profile_encryption.sql` creates profile-cascading wrapped keys and a separate `profile_key_tombstones` journal without a profile foreign key. Its trigger forbids deletion or changing the original profile/key/staging identity; it allows the destruction timestamp to move only from pending to completed.

1. The financial erasure transaction stages a key tombstone and deletes the live wrapped key. The usual profile cascade removes financial data. A rolled-back identity/financial erasure transaction preserves the live key and its usability.
2. After successful commit, the caller awaits `finalizeErasure(profileId)`. It passes the staged expected key identifier to the independent provider. Before writing a new destruction marker, the local provider requires that expected private 32-byte wrapping key to exist in its configured vault; an absent or invalid file leaves the intent pending. This prevents accidentally changing the vault directory from certifying destruction of a key still usable in the original directory. A no-DEK intent can legitimately fence an empty profile. An existing valid destruction marker remains idempotent. The provider persists its irreversible fence and destroys the profile's wrapping keys; the database then records completion.
3. A provider failure or crash leaves a durable pending intent. `recoverPendingErasures()` retries at boot and returns aggregate counts. The staged tombstone already blocks decryption and new encryption; the caller must not present a pending key-provider operation as completed destruction.
4. Restoration replays the separately protected deletion journal before traffic or jobs resume. `exportKeyTombstones` exposes only profile/key IDs and staging/completion timestamps, never wrapped keys. `replayKeyTombstones` is idempotent, removes any restored live wrapped key and preserves monotonic completion. It runs in the restore transaction.
5. After journal replay, finalization always checks the current independent key provider, including when the imported journal says destruction already completed. A restored completion timestamp alone does not prove that a different vault has destroyed its key.

Per-profile key destruction does not implement partial transaction deletion while retaining other rows. Separate source/row tombstones, plaintext logs, exports, authorized shared records, provider records and other processors still need their own deletion rules.

## Verification

Fourteen primitive and eight financial-storage integration tests passed against fresh PGlite and an isolated real PostgreSQL database (`lilleri_encryption_vaultguard_20261003`) on 2026-10-03. Eight deletion-aware restore tests also passed in the targeted run. The primitive tests cover repeated-plaintext nonce variation; UTF-8 round trips; profile/table/column/row binding; nonce/ciphertext/tag tampering; unknown formats and malformed encoding; domain-separated blind indexes; signed 64-bit financial preservation; JSON bounds; financial erasure rollback; durable pending-provider retry; wrong-vault destruction rejection; immutable/idempotent tombstone replay; vault reopen, permissions and symlink rejection; crash-marker cleanup; and a separately restored old database that cannot decrypt against the current destroyed vault.

The integration tests preserve legitimate legacy plaintext that resembles the ciphertext prefix or JSON wrapper, including CSV mapping names. They prove idempotent lossless upgrade across transaction fields, source payloads, manual audit reasons and saved CSV mappings/history. Upgrade failure rolls back all changes and restores both immutable audit guards; existing encrypted values are authenticated against their profile/table/column/row context. The tests also exercise scoped financial HTTP reads, paging, sync replay, eleven-file ZIP, manual transactions, description-based rules, CSV imports, reversal and decrypted audit/export. Transplanted ciphertext fails an HTTP read without exposing financial text or ciphertext. Successful deletion commits the financial cascade before independent key destruction. Its certificate distinguishes actual completed local destruction, outstanding provider revocations and unverified processors; a key-provider outage returns an honest pending status backed by a durable retry intent.

This proof is bounded to synthetic data and the current independent vault. Real-role provisioning, full non-owner PostgreSQL isolation, deletion-aware restore acceptance and final integrated totals belong to the repository's combined validation record.
