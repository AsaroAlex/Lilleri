# Explicit category rules in the local synthetic application

**Date:** 2026-10-03 · **Status:** Implemented category-rule vertical slice; broader E10 actions and live-bank beta remain open.

A saved rule starts as an inactive draft. Editing also turns an active rule into a draft. The user sees a retroactive preview, including matching movement IDs, affected classifications and movements protected by direct corrections, before applying the rule. Applying enables the same deterministic condition for existing and future matching movements. Disabling restores the classifications derived from the remaining tiers. No command edits amounts, transaction identities, account ownership or reconciliation decisions.

Conditions are combined with AND: exact merchant key, literal description contains/equals, inclusive absolute amount bounds in decimal integer minor-unit strings and an explicit currency, owned account, provider transaction kind and debit/credit/zero direction. Bounds use `bigint`; text uses Unicode NFKC, Italian lowercase and collapsed whitespace, without regular expression execution. Empty conditions, unknown keys/categories/actions, oversized text, invalid bounds and unknown currency codes are rejected. An exact PayPal/SumUp/Nexi/Stripe intermediary alone also requires an account or descriptor constraint; this finite demonstrative guard does not guarantee identification of all ambiguous merchants. At most 100 saved rules and 10,000 movements per preview are supported locally.

A direct transaction correction wins. An enabled explicit rule then outranks merchant preferences and the global dictionary. Higher priority wins; equal priority orders by rule ID and differing category actions produce conflict evidence and an inbox review item. These deterministic confidence values are not a measured accuracy claim. Source evidence identifies the rule and its revision.

Every mutation takes the same profile lock as ingest and feedback, resolves the rule within that profile, and compares the caller's revision. Preview runs in a repeatable-read snapshot. Its opaque digest binds canonical transaction IDs/revisions/content hashes, feedback, preferences and rule revisions/states. Apply recomputes that digest under the lock; changes return `409 rule_changed` before any rule or event write. The client refreshes the list and requires a new preview and explicit gesture, without replaying stale commands. The digest is a concurrency token, not an authorization credential.

`classification_rules` persists the versioned definition and state; `rule_events` stores command history, previous definitions and affected IDs, with a composite profile/rule foreign key. IDs and revision counters survive provider replay. Export includes both tables. Profile erasure cascades both. Archive keeps the historical record disabled. Undo restores the immediately preceding definition as an inactive draft: activating restored conditions always requires a new preview. The UI states this requirement explicitly. Undo is not a general multi-event history traversal or a 30-day category-migration reversal.

Endpoints are `GET/POST /v1/rules`, `PATCH /v1/rules/:id` with `{revision, definition}`, and POST `preview`, `apply` with `{revision, previewRevision}`, or `state` with `{revision, action: disable|archive|undo}`. A trusted per-request identity resolver constructs the scoped service; request bodies cannot select a profile. The default demo continues to use its configured synthetic profile. Local membership/session checks are separate from these concurrency guards.

Verification adds seven engine regressions for exact arithmetic, all-condition matching, literal text, sign/zero, isolation, sticky correction precedence and conflicting rule priority. Eight integration cases exercise draft/apply/replay/event persistence, sticky locks, source/feedback invalidation, competing commands, archive/undo, foreign ownership, overlapping-rule conflict review and HTTP validation. Eight integration cases passed against PGlite on 2026-10-03; the original seven also passed against PostgreSQL 16.15. Final repository-wide PostgreSQL verification uses a fresh isolated fixture database because concurrent draft migration development changed the shared test store’s recorded checksum; the guard correctly rejected that history. Expo component typechecking passed; native-device accessibility and store release are not inferred.
