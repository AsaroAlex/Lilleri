# Durable synthetic acquisition

This implementation exercises E03/E04 with an explicitly synthetic adapter. Provider metadata declares its own unattended refresh-attempt budget, fixed UTC window, maximum page/window sizes and snapshot semantics. The default fixture declares four unattended refreshes per 24 hours; the separate local free policy permits one per UTC day. Unknown budgets, unsupported user presence and inactivity beyond the configured limit do not produce provider calls. These fixture declarations are not measured bank coverage, live contracts or a refresh SLA.

## Transactions and provider I/O

`SyncCoordinator` receives a server-derived profile scope. Start, claim, checkpoint and final application use separate committed transactions. The profile/connection/job lock order serializes consent and quota decisions. A refresh reservation and lease are committed before `openSync`; HTTP/provider work runs outside SQL locks. Reservations cannot be refunded by directly deleting their journal or job. A retry of a valid snapshot checkpoint does not request or charge another refresh. A crash before a snapshot is recorded conservatively charges the next actual refresh attempt.

Every page, checkpoint and final write rechecks the current consent generation, lifecycle state, lease epoch/token and deadline. Pause, revoke, source erasure, a changed generation or an expired/replaced lease prevents a delayed result from entering the ledger. Provider failures, real retry-after values, bounded timeouts and expired snapshots have explicit outcomes. There is no same-request retry sleep. The active `enabled` setting prevents new claims, including resume of previously created jobs; re-enabling preserves their captured limits and checkpoint.

The synthetic adapter accepts a captured server observation instant. It leaves legacy demonstration transaction/booking dates unchanged, partitions its known separate CSV/manual examples before the new bank port, and rejects malformed clock values. Actual returned pages are validated without silently filtering an unexpected source. Future or impossible source observation timestamps fail before checkpoint or freshness writes.

## Bounded progress and exact application

Initial acquisition starts at provider-declared history. A missing start remains unknown and creates a history-gap issue. The default through-date and previous acquisition date follow the locked profile's IANA calendar; transaction calendar DATE values are never shifted through a timezone. Future interval rejection uses that same profile date. Subsequent defaults begin at the earlier of the trailing correction start and the previous successful acquisition date, so a long absence does not skip its unsynchronised gap. Unattended daily budgets keep their explicitly declared UTC boundary. Requested intervals are split into provider-sized windows of at most 14 days. Accounts, pages, records, cursor bytes, staged bytes, wait slices and retained-stage duration have central validated bounds.

The complete bounded snapshot is staged with profile/job authenticated encryption when profile encryption is configured. Each resume processes at most the job's captured page limit. Partial work never advances account balances, saved freshness or canonical financial rows. The final transaction applies all accepted observations/accounts/transactions, records the exact payload outcomes and sync run, writes any configured server-time source-fact proof, then removes the checkpoint. A proof failure rolls back the entire financial application. The raw checkpoint's original deadline is never extended; bounded cleanup physically removes expired content even while acquisition is disabled.

Every payload record has a classified outcome, including duplicate/superseded observations and rejected status regression. Canonical amounts use integer minor units. Booked source absence requires two distinct complete fetches and creates attention while retaining the original amount and user edits. Unknown/incomplete coverage suppresses deletion claims. Absent pending entries remain conservatively reserved. Only an explicit same-source provider link with the same account, currency and amount replaces the active pending overlay; retained canonical history remains available to the owner.

A balance is comparable only with a declared booked meaning, date, reliable opening anchor and complete matching interval/currency. Otherwise the result is `not_comparable`. A verified mismatch produces an issue without a fabricated balancing transaction. Current Inbox attention uses the latest completed balance/history report and unresolved source presence, deduplicates old issues, suppresses quiet/private relations and private account groups, and returns at most 100 items. Ownership exports retain the complete issue/job/presence/budget history and original ledger references; they exclude stage content, lease tokens and captured operator/provider-policy documents. The validator rejects duplicate audit identities, broken scope/references and impossible audit chronology.

## Server and client hooks

`POST /v1/sync/start` accepts only a connection, request ID, optional calendar interval and `user_present` mode. `POST /v1/sync/:id/resume` accepts an empty body and one bounded user-present slice. Reports and connection job history are normal read-scoped routes. The legacy sync endpoint waits only within a captured finite slice limit and preserves its completed-count response. Connection auto-sync runs after the connection transaction commits.

The serial background pump reloads configuration before each bounded batch, visits profiles with a volatile pagination cursor, and awaits current work on shutdown. It resumes only `unattended` jobs: a stored user-present intent does not establish user presence for a later background retry. User-present work waits for an explicit gesture or trusted foreground opening. The foreground refresher receives only server-resolved profile/session/editor context after the overview response transaction commits. It coalesces concurrent openings, debounces sessions with central settings, caps volatile session state, and performs one user-present slice. Viewers, disabled configuration and unsupported/paused/revoked sources produce no provider work. It has no timer or polling loop, and shutdown awaits both configuration reads and provider work.

The connections panel shows durable job history/progress and actual degraded reasons in Italian and British English. An explicit update starts and resumes once; continuing requires another gesture. Checking progress reads only. Reopening reloads unfinished jobs. Responses, notices, request IDs and callbacks are fenced by the profile/session epoch; uncertain start responses reuse the request identity. The overview refresh runs only after completion.
