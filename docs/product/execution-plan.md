# Repository execution plan

**Snapshot:** 2026-10-03. **Scope:** the founder's request to execute the repository plan remains active. This document accounts for all epics E00–E39; it does not replace their acceptance criteria in [backlog](backlog.md), [MVP](mvp.md) or [roadmap](roadmap.md). Documentation is English; product copy is Italian.

## Delivery boundary and evidence

The [37 initial deliverables](../STATUS.md#coverage-of-the-37-requested-deliverables) have a documented foundation and working synthetic implementation. They are distinct from the full future P0 beta, P1 launch, P2 expansion and Later programmes. Completing an initial foundation does not complete every story in those programmes.

The verified local baseline contains exact-money/domain/provider engines, a persistent scoped API, opt-in loopback authentication, reconciliation revisions, category rules, manual accounts/CSV preview and import, profile settings/entitlements, durable revocation and expiring raw payloads. Authenticated profiles start empty. Bank fixture names do not establish supported real institutions. The demo and local-auth modes reject production configuration.

The completed final verification is **264 distinct tests: 167 core and 97 API**. The same 97 API scenarios passed the PostgreSQL-configured integration suite; legacy/reopen cases deliberately retain PGlite. The database has **12 checksum migrations**, `pnpm check` completed **22 tasks** and `pnpm build` completed **10 tasks**, including Next and Expo web export. Scheduled local payload cleanup (**E18.5**), ZIP download (**E18.2**) and the original synthetic evaluation runner (**E25.3**) are now integrated and tested. Browser evidence covers **17 financial and 16 identity groups**, with zero JavaScript errors. These are local capability increments; remaining story acceptance below stays open. See [STATUS](../STATUS.md) for commands, source scope and limits.

Status terms below apply to the named capability, not automatic completion of an epic: **delivered local** means implemented with synthetic local evidence; **partial** means some stories or criteria remain; **open** means the described capability is absent; **external gate** identifies a concrete prerequisite for real operation or acceptance. An external gate does not suspend independent local software work.

## Reconciled requirements

Renewal scheduling follows actual adapter metadata and configurable offsets before consent expiry or another explicitly mapped required renewal action. Consent, SCA, session and token dates remain distinct. There is no universal 180-day lifetime or day-150/170/178 timer. Unknown dates must not generate invented deadlines. This interpretation follows the current [consent model](../compliance/consent-model.md); older PRD examples remain historical requirements to reconcile when those screens are implemented.

The 25 reconciliation scenarios are a baseline catalogue, not evidence of 25 implemented features. Each entry needs its intended outcome, story/priority and supported/incomplete/expected-unsupported status. Run and report actual supported assertions; keep unfinished P0 open, and require them before cleared beta. P1/P2/Later capability guards may verify safe refusal, but an expected-unsupported outcome is never a feature PASS. Existing limited refund/cash behaviour does not establish complete split, reimbursement or settlement-period acceptance.

The remaining technical rows stay active even while provider, legal or empirical prerequisites are pending. Release/expansion gates control real operation and claims; they do not turn unimplemented local work into completed delivery.
